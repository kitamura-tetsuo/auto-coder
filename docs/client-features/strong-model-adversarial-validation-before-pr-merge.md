    configuration:

Used by PR adversarial validation when [backend_pr_adversarial_validation] is absent, and by Issue specification/decomposition analysis when [backend_issue_adversarial_validation] is absent."
      - "[backend_pr_adversarial_validation]: Optional dedicated order / default / model for PR adversarial validation only, in ~/.auto-coder/llm_config.toml. When present it is authoritative for PR validation: an order/config that resolves to no read-only-review-capable backend blocks PR validation rather than falling back to [backend_adversarial_validation]."
      - "[backend_issue_adversarial_validation]: Optional dedicated order / default / model for Issue specification analysis and Issue parent/child decomposition analysis only, in ~/.auto-coder/llm_config.toml. When present it is authoritative for both Issue analysis paths: an order/config that resolves to no read-only-review-capable backend blocks that analysis rather than falling back to [backend_adversarial_validation]. Configuring this section never changes PR adversarial validation's backend selection."
      - "ENABLE_ADVERSARIAL_VALIDATION / pr_adversarial_validation (AutomationConfig): Toggle feature on/off (default: True, overridable via AUTO_CODER_ENABLE_ADVERSARIAL_VALIDATION env var or pr_adversarial_validation setting)."
      - "MAX_ADVERSARIAL_VALIDATIONS / [adversarial_validation].max_reviews (AutomationConfig): Specifies maximum adversarial review executions for a PR (default: None for unlimited, overridable via AUTO_CODER_MAX_ADVERSARIAL_VALIDATIONS env var). When reached on a green PR, adversarial validation is skipped and PR proceeds to merge."
    behavior:
      - "Runs after normal CI / GitHub Actions checks are green and before merge eligibility."
      - "Maximum Adversarial Reviews Gating: When MAX_ADVERSARIAL_VALIDATIONS (or [adversarial_validation].max_reviews) is configured and the PR has reached or exceeded that count of adversarial review runs, further validation is skipped and the green PR proceeds directly to merge."
      - "Issue Eligibility: Eligibility and validation context share one verified-oracle resolver for candidates found in PR body, title, or branch metadata. A PR with no candidate Issue is outside validation scope and continues through other merge requirements without a validation result. A candidate that is missing, unavailable, or resolves to another PR fails closed instead of being treated as intentionally Issue-less."
      - "Codex Review Ordering: For Issue-backed PRs, a Codex GitHub review summary from chatgpt-codex-connector[bot] must reach Code Review / Completed before adversarial validation starts. A summary that is still running defers the PR to a later processing iteration without a fixed delay. Comment lookup uses a strict, cache-revalidated REST path so API failures or stale cached summaries cannot be mistaken for absent/completed review activity."
      - "Optional Codex Stage: If no Codex review summary exists, adversarial validation runs normally. A Completed summary is sufficient even without a +1 reaction and regardless of whether its reviewed commit differs from the current head."
      - "Review Feedback Ordering: Strict tri-state review-thread checks prevent adversarial validation and merge until actionable feedback is resolved. A review-thread API error is distinct from an empty thread list and fails closed. After observing a Completed Codex summary, Auto-Coder performs a fresh second thread check before starting adversarial validation, closing the completion/finding TOCTOU window; validation remains pinned to the current PR head."
      - "Changed-Head Finding Revalidation: An unresolved finding published by the authenticated adversarial-reviewer App for an older head remains merge-blocking but does not prevent independent validation of a current head that has no applicable verdict, even when the configured adversarial-review count limit has been reached. Reviewer identity matching is case-insensitive and treats the App slug and its trailing [bot] login form as equivalent, so GraphQL thread authors match the authenticated reviewer identity. Revalidation does not require an implementation-agent reply or commit attribution, and only an ADDRESSED disposition validated against the still-current exact head may resolve the old thread; unchanged heads retain feedback-delivery deduplication and ordinary unresolved-thread gating."
      - "Fail-Closed Design: PASS is only produced for an explicitly parsed, internally consistent PASS with 0 blocking findings; all empty, malformed, contradictory, or inconclusive responses block PR merge."
      - "Parse Failure Diagnostics: Empty responses, invalid JSON, schema violations, contradictions, and unrecognized formats remain fail-closed and are logged with PR/attempt/backend/model context, a redacted 2,000-character preview, and the structured LLM interaction-log path."
      - "Review Anchor Boundary: Anchor lines are positive JSON integers or null. Positive decimal strings from an LLM are normalized to integers, while booleans, non-positive values, fractions, and malformed strings produce a structured schema ERROR. Validation execution and parse errors remain processing errors, and any published COMMENT is identified as an error diagnostic rather than a successful adversarial review."
      - "Full Effective Response Retention: The structured LLM interaction log retains the redacted combined CLI response (stdout and stderr), while normal operational and trace logs remain bounded."
      - "PR Result Publishing and Versioned SHA Deduplication: Publishes the parsed validation status, summary, structured findings, requested dynamic check, and parse diagnostic to the PR conversation for the exact validator version and validated head SHA. Before invoking the reviewer, Auto-Coder reads that durable comment: the same SHA is not sent to the same validator version again, a saved PASS proceeds to merge checks, and a saved non-PASS remains blocked until the PR head or validator version changes, except that a new material reply to an unresolved change-provenance clarification makes the same SHA eligible for independent revalidation. The exact clarification discussion is fingerprinted in the resulting review so unchanged replies do not repeatedly rerun validation. Failure to read prior comments fails closed without invoking the LLM. Raw CLI event streams are excluded from every comment field, individual fields are bounded, requirement coverage is summarized by status with bounded non-passing IDs, and oversized reports are bounded globally. Codex uses its dedicated final-message output for the validator response, while compatibility JSONL parsing consumes stdout only. If a nested container cannot start Codex's read-only bwrap sandbox, a non-LLM preflight enables a no-approval fallback only inside the disposable detached validation worktree."
      - "Implementer Change-Provenance Clarification: When every applicable Issue requirement is VERIFIED or justified IRRELEVANT but the reviewer cannot establish why one or more material changed files or related groups belong to the PR, the result is an INCONCLUSIVE clarification blocker rather than an Issue requirement violation. The authoritative review publishes exactly one aggregated thread listing all unexplained groups and asks whether each is directly intentional, mechanically generated from an intentional change, or unrelated/accidental, including the causal reason for intentional/generated changes. Publication prefers a supported nested-review line anchor on an unexplained file, falls back to any represented changed-file line, and uses the dedicated reviewer App's separate file-level review-comment endpoint when binary, large, or unsupported diffs expose no line anchor. An unanswered thread blocks PASS and merge without requesting code changes or a new commit and is not duplicated on unchanged processing. A material marked reply enables same-SHA revalidation; the reply remains an unverified navigation aid, and the reviewer must independently verify it against repository evidence. Verified provenance can resolve the thread and allow same-SHA PASS. Resolution and verdict publication are recoverable as one transition: after an apparent App publication failure, Auto-Coder first re-reads the authoritative fingerprinted verdict and keeps the thread resolved if the expected result is already durable; otherwise it reopens the thread, with failed reopen attempts durably recorded for startup reconciliation. If delayed visibility exposes a saved PASS only on the next cycle while the provenance thread is unresolved, that PASS forces same-SHA revalidation and resolution instead of bypassing the thread gate. A STILL_VALID or INCONCLUSIVE disposition remains non-PASS and publishes its concrete rationale and evidence both in the existing clarification thread and in the authoritative review summary; both publications use the dedicated reviewer GitHub App identity and never fall back to the ordinary GitHub credential. Accidental or contradicted changes are explicitly identified for removal or correction."
      - "Dedicated GitHub App Review Publishing: Fresh validation verdicts are published as native reviews from the separately configured auto-coder-reviewer GitHub App, pinned to the validated head SHA. PASS maps to APPROVE, NEEDS_FIX maps to REQUEST_CHANGES, and other outcomes map to COMMENT. Authentication, head-race, or publication failures block further processing without falling back to the normal user credential."
      - "Codex Structured Output Handling: For no-edit `codex --json` reviewers, requests the final assistant payload through Codex's dedicated `--output-last-message` file while retaining the JSONL stdout and stderr diagnostics in the full interaction log. If no final payload is written, strict JSONL parsing remains the compatibility fallback; failed, incomplete, or contaminated fallback streams remain blocked."
      - "Codex Usage-Limit Diagnostics: Successful Codex JSONL item payloads are reviewer evidence and are excluded from usage-marker detection, preventing source code or command output containing phrases such as `usage limit` from causing false backend rotation. Explicit top-level error events and stderr diagnostics remain eligible limit signals."
      - "Single-PR Metadata Completeness: REST PR normalization retains nested head/base refs and SHAs plus author identity, so `process-issues --only <PR>` uses the same merge and isolated-worktree validation inputs as normal candidate enumeration."
      - "Oracle Acquisition Required for Eligible PRs: An Issue-backed PR fails closed (BLOCKED) if its linked specification or acceptance criteria cannot be acquired after validation starts; an intentionally Issue-less PR is skipped rather than assigned a validation status."
      - "Backend Independence: Uses independently configured strong model without silently falling back to the general implementation backend."
      - "Complete File-Aware Evidence: Fetches the authoritative changed-file count independently from raw diff evidence. PRs with more than 300 changed files require human review and are BLOCKED from automatic merge; a missing authoritative count also fails closed. For PRs within that limit, splits diffs by file and supplies every retrieved changed-file patch to the reviewer in full, with no Auto-Coder-local character budget that omits, truncates, samples, or selects files; the complete changed-file path manifest is likewise rendered in full. Only a genuine upstream gap — the authoritative changed-file count exceeding what the raw diff actually returned — is recorded as explicit unverified evidence, listed by path. Git C-style quoted paths are decoded, while unparseable headers fail closed."
      - "Explicit Issue Contract: A directly linked Issue with a Markdown heading exactly named Requirements uses only valid REQ-NNN entries in that section as its normative manifest. Requirement IDs may be plain text or Markdown inline code, including a colon inside or immediately after the backticks. Source IDs and text are preserved, with #issue/REQ-NNN disambiguation when linked Issues reuse an ID. Parent Issues and all prose outside that section remain reviewer context only. Duplicate, malformed, or empty explicit contracts fail closed; an Issue without the section uses legacy extraction on its direct body only, and prompts identify explicit, legacy, or mixed manifest mode."
      - "Coverage-Gated PASS: Every authoritative manifest entry receives the existing fail-closed coverage treatment. Reviewer output must provide a VERIFIED or justified IRRELEVANT coverage entry with evidence for every exact manifest ID; missing, duplicated, unknown, VIOLATED, or UNVERIFIED IDs prevent PASS regardless of any boolean completeness claim. Unknown IDs and VIOLATED entries without concrete findings fail closed as schema/contradiction ERRORs instead of being silently ignored or downgraded to finding-free INCONCLUSIVE. Every partial or unavailable per-file patch is also recorded explicitly, so a model PASS is deterministically converted to INCONCLUSIVE while any material file evidence or Issue requirement remains incomplete."
      - "Demonstrated-Finding Verdict Precedence: Only a counterexample classified DEMONSTRATED and referencing an exact stable ID from the deterministic Issue requirement manifest, with a reachable state/action path, required behavior, actual conflicting behavior, and implementation or focused dynamic-check evidence, is normalized to NEEDS_FIX. Unknown or invented finding IDs are rejected deterministically. Explicitly UNVERIFIED suspicions cannot be re-promoted by any top-level label (including PASS) and remain INCONCLUSIVE; coverage and infrastructure failures still fail closed."
      - "Independent Finding Lifecycle and Requirement Coverage: Requirement coverage is evaluated per stable Issue ID, while review-thread disposition is evaluated only against that thread's recorded concrete counterexample. Fixing one path resolves its thread even if another path keeps the same requirements VIOLATED; the new path receives a current finding, and an old finding is reopened only if its own counterexample regresses. Every demonstrated finding requires both a concrete root-defect identity and an independently actionable correction/test-oracle identity; omission fails schema validation closed. Grouping uses these structured identities rather than byte equality of reviewer prose, and preserves all requirement-specific path, evidence, contract, counterexample, and oracle descriptions. Equivalent sibling paths may share both identities only when their root failure, correction, and test oracle match and every affected path is enumerated; materially different corrections remain separate. Review summaries omit resolved dispositions but retain the current rationale and evidence for unresolved STILL_VALID and INCONCLUSIVE dispositions, because ordinary dispositions are not otherwise republished into their existing threads."
      - "Specification-Gap Separation: Material reachable behaviors that require a new policy absent from the authoritative linked Issue are represented as structured specification gaps, never findings or new verdicts. Defined requirements continue to receive complete coverage and retain verdict precedence; insufficient evidence for a defined behavior remains INCONCLUSIVE/BLOCKED rather than becoming a gap. Human-facing reviews distinguish gaps from defects, state that no policy was selected, and preserve neutral candidate options only as non-authoritative discussion."
      - "Specification-Gap Merge and Repair Gates: PASS may coexist with specification gaps, but automatic merge requires PASS, no findings, and no gaps. A gap-only PASS receives a COMMENT rather than an approval and remains manually mergeable. When findings coexist, normal repair continues while the repair prompt expressly forbids implementing candidate policies or mutating/creating Issues solely for a gap; durable same-SHA reports remain blocked from automatic merge."
      - "Convergent Incremental Rereview Policy: The initial review remains a broad, full-coverage, fail-closed falsification pass over the complete Issue contract. After NEEDS_FIX and a new head, the persistent reviewer classifies every prior blocker as fixed, still violated, or regressed; revalidates requirements affected by prior blockers, corrective changes, shared invariants, or potentially invalidated evidence; and inspects the corrective change for related regressions or symptom-masking workarounds. A previous VERIFIED or IRRELEVANT status may be carried forward only after confirming that the corrective changes do not invalidate its implementation, tests, scope, or other evidence; the rereview must emit every stable requirement ID again with evidence identifying the prior head and non-impact basis. Uncertain impact remains UNVERIFIED/INCONCLUSIVE. It does not restart unrestricted exploration: a newly noticed defect can block at any iteration only when supplied evidence demonstrates a reachable violation that is material to an explicit Issue requirement. Low-impact boundaries, speculative robustness, hardening opportunities, and test-only improvements do not restart the repair loop unless they meet that material standard."
      - "Bounded Adjacent-Counterexample Exploration: After confirming a violation, the reviewer examines at most eight additional candidate boundaries sharing its requirement, transition, lifecycle invariant, root cause, or authoritative-data boundary. It bundles independently demonstrated sibling cases by structured root/correction identity, distinguishes sibling manifestations from independent defects, and discards unsupported suspicions rather than turning them into blocking findings."
      - "Evidence Recovery and Scoped Uncertainty: Initially supplied patch evidence is a navigation hint rather than the decision authority. The reviewer makes at most eight explicit recovery attempts through current-repository inspection, current-PR retrieval, focused execution, or tests; records recovered, unavailable, and irrelevant evidence; and scopes each attempt to materially dependent requirement IDs. Independently recovered current-head evidence can satisfy file coverage. Every requirement left UNVERIFIED in an INCONCLUSIVE result must have its own scoped recovery attempt and decision-critical gap, while gaps for already VERIFIED or IRRELEVANT requirements are rejected and cannot satisfy another requirement's contract. INCONCLUSIVE is requested only after useful bounded recovery is exhausted and must name the smallest concrete decision-critical gap, while unaffected requirement coverage remains intact."
      - "Invariant-Oriented Repair: Corrective prompts require the implementation agent to repair the shared correctness invariant rather than only the example and to evaluate adjacent transitions, authoritative sources, restart/persistence, ambiguous provider results, ordering/races, and strict regression coverage."
      - "Dynamic-on-Suspicion Contract: Supports dynamic test execution when requested by the reviewer; failure or inability to execute dynamic checks fails closed."
      - "Post-Validation CI Authority: Immediately before merge, production refreshes and reapplies the exact-head CI eligibility gate. A newer pending, failing, unavailable, or otherwise non-passing observation replaces earlier green admission evidence and prevents merge even when adversarial validation returns PASS. If accepted webhook knowledge fences that refresh during the final head check, production obtains and applies another authoritative CI observation before invoking the merge mutation. CI delivery acceptance/fencing and the final authority-proof/merge mutation are serialized so a delivery cannot become accepted between those boundaries."
      - "Final merge CI reads own a bounded read phase from the post-validation refresh through the head check, optional invalidation retry, and authority-guarded merge call. Direct PR processing needs no caller-created phase; leaving this block clears its observations. New CI deliveries still fence the active phase and prevent stale green evidence from authorizing merge."
      - "Exact-Head Dynamic Evidence: Requested adversarial checks execute directly in the detached validation worktree through its test script, with repository HEAD asserted before and after execution. A known SHA mismatch is a merge-blocking ERROR, an unverifiable SHA is INCONCLUSIVE, and neither kind of invalid evidence may resolve an existing material test-oracle gap or review thread."
      - "Material Gap/Thread Convergence: Trusted current-head evidence closes a persisted material test-oracle gap when either the validator explicitly returns the same scoped gap as RESOLVED/INVALID with resolution evidence or an exact representing review thread receives an evidence-backed ADDRESSED disposition. This includes same-head recovery after the thread was already resolved and excluded from claimed-thread classification. Proven semantic closure is persisted before thread resolution even when an unrelated provenance gate keeps the overall verdict INCONCLUSIVE. GitHub's resolved UI state alone is never closure evidence; persistence failure aborts validation before thread projection, leaving the prior OPEN checkpoint recoverable at the same head."
      - "Requires demonstrated, reachable behavioral counterexamples: `Given state S, when reachable action A occurs, then specification requires R, but implementation demonstrably produces X`; test gaps, hardening opportunities, and assumption-dependent suspicions do not independently block."
      - "When NEEDS_FIX is determined:"
        - "Blocks PR merge."
        - "Publishes the concrete findings to the PR conversation without checking out or modifying the local PR branch."
        - "For a PR associated with an existing Codex Cloud task, sends the complete bounded validation report to that task as a follow-up fix request. Delivery is recorded with a validator-version and head-SHA marker so a saved NEEDS_FIX result can be delivered after restart without being resent on every processing loop."
        - "For other PRs, the PR author or other recipient remains responsible for applying the correction. After a new commit and green CI, Auto-Coder validates the new head SHA and only merges after PASS."
