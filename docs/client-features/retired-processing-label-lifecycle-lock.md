github-pending-work-scheduler:
  description: "Connects the durable GitHub pending-work store to the daemon lifecycle so retained obligations resume automatically after admission or startup, rather than only being observable through direct store manipulation (Issue #1920)."
  documentation: "src/auto_coder/github_pending_work.py"
  behavior:
    - "`AutomationEngine` owns a `PendingWorkScheduler` (one per process) that runs as its own supervised task inside `start_automation`, started before startup reconciliation so restart-surviving obligations are never orphaned by a fresh enumeration."
    - "A semantic stage (e.g. startup reconciliation, Issue/PR evaluation, publication) registers a `StageHandler` (`dispatch`/`recover`) with the scheduler via `register_handler(stage, handler)`; an obligation for an unregistered stage is left retained and reported as blocked rather than discarded or completed."
    - "The scheduler wakes on the earliest due deadline or an explicit `wake()` call (e.g. an admission-change notification) instead of polling tightly; a due-but-not-actionable obligation waits at least one poll interval (default 1s) before the next attempt, never a zero-delay loop."
    - "Obligations track a `status` of waiting or running. Dispatch claims a row as running before invoking its handler; a controller that stops (crash or graceful shutdown) while a claim is running leaves that row running, and the next scheduler start routes it through the handler's `recover()` entry instead of a fresh `dispatch()` or treating it as complete."
    - "A stage handler's error result re-defers only its own still-unfinished effects through the existing throttle/admission-deferral accounting in `PendingWorkStore.defer()`; completing one effect never discharges an independent sibling effect."
    - "`auto-coder pending-work list` and `auto-coder pending-work retry --repository --entity --stage [--revision]` expose the store for operators: list is read-only, and retry clears only the selected obligation's retry deadline and throttle count (REQ-007) without touching confirmed effect receipts or any other obligation; the retried dispatch still goes through the shared governor."
    - "`AutomationEngine.get_status()` includes a `pending_work` snapshot (repository, entity, stage, revision, reason, status, next-eligible time, unfinished effects, and whether it is blocked and why) for daemon status visibility."
    - "A preflight-schema database (no `status` column) is migrated in place on open; its rows default to waiting so pre-existing retained work is preserved rather than dropped."

resumable-startup-reconciliation:
  description: "A deferred or throttled startup GitHub scan retains recoverable work and retries automatically instead of terminating the daemon (Issue #1921)."
  documentation: "src/auto_coder/automation_engine.py"
  behavior:
    - "`start_automation` registers a `startup-reconciliation` stage handler with the pending-work scheduler (immediately after creating its task, before any await) and runs the first startup attempt inline: open-PR ownership discovery, then strict Issue/PR enumeration."
    - "A `GitHubRequestError` from that attempt (a local admission deferral or an actual GitHub throttle, authentication, or forbidden response) does not terminate the daemon: it is retained as a durable pending-work obligation keyed by a stable repository-scoped identity (`WorkIdentity(repo_name, \"startup\", \"startup-reconciliation\")`, stable across restarts), and the already-running pending-work scheduler retries it independent of the ordinary worker pool. Any other exception is a genuine defect and continues to propagate and stop the daemon, unchanged from before."
    - "The ordinary worker pool, producer loop, and invalidation loop do not start until startup reconciliation succeeds; `start_automation` waits on that outcome (or on shutdown) without blocking the event loop, so webhook receipt, status reporting, and graceful shutdown remain responsive while recovery is incomplete."
    - "Every retry -- whether the inline first attempt or a scheduler-driven dispatch/recover -- performs a complete fresh open-PR-ownership discovery and Issue/PR enumeration; a later-page failure is never combined with an earlier successful page as partial success."
    - "Open-PR ownership discovery failure (deferred or throttled) is no longer silently swallowed: `ImplementationSlotRepository.reconcile(discover_open_prs=True)` propagates it so the same durable obligation covers both ownership discovery and entity enumeration, preserving existing owners until discovery completes."
    - "On success, any pending-work obligation retained for this repository's startup-reconciliation identity is cleared (superseded or its effect completed), so a later timer never repeats a full repository enumeration merely because time passed; `AutomationEngine.get_status()['pending_work']` continues to expose an incomplete cycle's reason and next-eligible time via the existing pending-work snapshot."

merge-operation-state:
  description: "Durable state for one PR's approval-then-merge mutation sequence, modeling automatic approval and merge as independent effects with per-attempt ownership and correlated delivery receipts so a restart, duplicate notification, or stale in-flight result can never re-post an approval, re-merge, or silently discard evidence that a mutation already happened (Issue #1937, merge-recovery 1/3)."
  documentation: "src/auto_coder/merge_operation_state.py"
  behavior:
    - "`MergeOperationStore` (SQLite, `~/.auto-coder/merge_operation_state.db` by default) keys operations on `MergeOperationIdentity(api_origin, repository, pr_number)` and tracks, per operation: the expected head SHA, merge method, approval credential role, reviewer identity, a generation counter, and an `OperationStatus` (waiting, running, operationally_blocked, superseded, merge_confirmed)."
    - "Approval and merge are tracked as independent `EffectRecord`s with an `EffectState` of not_needed, not_attempted, running, confirmed_unsent, confirmed_rejected, confirmed_complete, or delivery_unknown; completing or waiting on approval alone never marks the operation merge_confirmed -- only merge reaching confirmed_complete (with approval not_needed or confirmed_complete) does."
    - "`get_or_create` is idempotent for the same expected head: a duplicate notification, a different entry point, a restart, or a merge-method/credential/reviewer metadata refresh never resets effects, deadlines, generation, or receipts. A genuinely new expected head bumps the generation and returns any not-yet-confirmed-complete effect to not_attempted while leaving the prior generation's history and receipts untouched."
    - "`reserve_attempt` grants at most one execution right per effect at a time (no duplicate mutation permission across entry points/threads); it is refused while the effect is already running, already confirmed_complete, delivery_unknown (awaiting explicit reconciliation), or the operation is operationally_blocked/superseded/merge_confirmed."
    - "Every reservation is stamped with a fresh `attempt_id` and the operation's current `generation`; `record_confirmed_complete` / `record_confirmed_unsent` / `record_confirmed_rejected` / `record_delivery_unknown` / `defer_local` all verify the caller still owns that exact `(attempt_id, generation)` pair before mutating current state -- a stale attempt (superseded by a newer head) is recorded only to the append-only `merge_operation_attempt_history` table and never overwrites the current effect, deadline, or receipt."
    - "Confirmed-complete receipts (`EffectReceipt`) carry a `ConfirmationSource` (own_response vs. state_observation) plus review ID/reviewer identity/target head for approval and merge commit SHA/target head for merge -- never tokens, Authorization headers, or raw request/response bodies."
    - "`recover_after_restart` reclassifies any effect left `running` (a controller that stopped between reserving an attempt and recording its outcome) as `delivery_unknown`; such an effect is not auto-retryable until an explicit reconciliation call resolves it, and is not converted to any other state merely by cancellation, timeout, requeue, or repeated recovery passes."
    - "`defer_local` implements the REQ-006 deadline floor: the new deadline is never earlier than `now + MIN_LOCAL_RETRY_INTERVAL_SECONDS` (1s), any `retry_after_seconds`, an explicit governor deadline, or the previously retained deadline, whichever is latest; a real throttle response only spends one retry per distinct `throttle_attempt_id` (duplicate redelivery is free), a purely local (pre-send) deferral never spends a retry, and one real throttle plus `MAX_THROTTLED_RETRIES_AFTER_FIRST` (3) further automatic attempts are tolerated before the operation becomes `operationally_blocked` with `throttle_retries_exhausted`."
    - "`operationally_block` durably records an authentication/forbidden failure; `manual_reset_effect` is the explicit operator escape hatch that clears a block/rejection/exhaustion for one selected effect only, without touching its receipt or its sibling effect."
    - "All persistence failures (reservation, receipt recording, reopening the store) raise `MergeOperationPersistenceError` rather than reporting success or silently degrading; existing rows are left intact, and no token/Authorization/secret/request-body value is ever persisted or logged -- new diagnostics go through loguru to stdout and the existing rotating log files, matching the rest of the codebase."
    - "This stage owns only the state model and its persistence boundary: interpreting real GitHub approval/merge responses, wiring this into normal PR processing, and connecting it to the pending-work scheduler are explicitly out of scope here and are owned by later child issues under #1936."

merge-operation-adapter:
  description: "Production GitHub adapter that turns one real approval or merge HTTP exchange into a correlated MergeOperationStore outcome -- confirmed complete, a typed deferral, an operational block, a definitive rejection, or an indeterminate delivery -- never a fabricated receipt or a guessed unsent (Issue #1938, merge-recovery 2/3)."
  documentation: "src/auto_coder/merge_operation_adapter.py"
  behavior:
    - "`attempt_approval`/`attempt_merge` reserve exclusive execution rights via `MergeOperationStore.reserve_attempt` before sending anything; a refused reservation (effect already not_needed/confirmed_complete/delivery_unknown/confirmed_rejected, or the operation blocked/superseded/merge_confirmed) returns `already_satisfied` with zero wire calls."
    - "Before posting a new approval, `attempt_approval` lists every page of `GET /pulls/{number}/reviews` via `get_ghapi_client()` and looks for the configured reviewer identity's *last decisive* review (ignoring COMMENTED/PENDING); if it is APPROVED with `commit_id` equal to the operation's expected head, the approval effect is satisfied via `ConfirmationSource.STATE_OBSERVATION` (the review id/principal/head is recorded) and no POST is sent. A different principal, a different head, a later CHANGES_REQUESTED/DISMISSED verdict, or a failed/partial page listing are never treated as valid approval evidence, and a listing failure is classified and recorded like any other mutation failure without ever reaching the POST."
    - "A fresh approval POST (`event=APPROVE`, `commit_id=<expected head>`) is confirmed complete via `ConfirmationSource.OWN_RESPONSE` only when the response carries a non-empty review id, `state == \"APPROVED\"`, and `commit_id` equal to the expected head; any other 2xx body (wrong head, missing id/state) is recorded `delivery_unknown` rather than fabricated into a receipt."
    - "A merge PUT is confirmed complete via `ConfirmationSource.OWN_RESPONSE` only when the response reports `merged: true` with a non-empty merge commit SHA; a 2xx body that fails either check is recorded `delivery_unknown`, never treated as a confirmed rejection."
    - "`reconcile_approval`/`reconcile_merge` are explicit, read-only entry points that only ever act on an effect currently `delivery_unknown` (otherwise `no_reconciliation_needed`); they never send a mutating request. `reconcile_approval` re-runs the same all-pages review lookup and only ever moves the effect forward to `confirmed_complete` on a positive match -- an unreachable/partial listing or the absence of a currently valid approval (including one later dismissed) leaves `delivery_unknown` completely unchanged, preserving the original mutation's uncertainty rather than guessing it. `reconcile_merge` performs one fresh authoritative `GET /pulls/{number}` and resolves to `confirmed_complete` only when `merged: true`, the PR's current head still equals the expected head, and `merge_commit_sha` is non-empty -- an external actor's merge counts, a different (later) head's merge does not, an open/unmerged/unreadable observation never flips the effect back to unsent, and a squash/rebase merge commit SHA is never compared against the head SHA."
    - "HTTP fault classification for both effects: 401/403 without throttle evidence -> `operationally_block` (authentication_failure/forbidden); 429, 403 with throttle evidence (remaining=0/valid Retry-After/secondary-rate-limit body), or any other real-throttle classification -> a real-throttle `defer_local` (spends one of the store's tolerated automatic retries); a local Governor admission refusal (e.g. mutation-spacing) -> a local, zero-spend `defer_local` carrying the Governor's own retry deadline; a mutation 5xx or any unwrapped transport/body-read exception -> `record_delivery_unknown`; a synchronous merge PUT's 409 -> `record_confirmed_unsent` (the mutation was rejected, never applied) followed by `store.supersede()` so the operation cannot be retried against the stale head; 405, 422 without throttle evidence, and any other unclassified 4xx -> `record_confirmed_rejected` as a cause-unspecified definitive rejection, never treated as license to try another method, endpoint, or credential."
    - "Exactly one mutating request (POST review or PUT merge) is ever sent per `attempt_*` call, plus only the review-listing GETs REQ-003 requires; no hidden internal retry, fallback method/CLI/endpoint/credential, or extra diagnostic GET is ever issued by this module."
    - "This module is adapter-only and intentionally unwired: it is not called from `pr_processor.py`'s normal merge path, `PendingWorkScheduler`, or any other production entry point in this issue -- that wiring, along with re-verifying merge-time approval validity, is owned by a later child issue under #1936. It performs no CI/review-pass judgment, provider repair, or Issue/session lifecycle mutation."

execution-scoped-structured-diagnostic-traces:
  description: "Versioned, execution-scoped structured diagnostic events and a read-only snapshot API, so dashboard/consumer code can distinguish independent evaluations, async jobs, and scheduler resumptions of the same Issue/PR without changing automation behavior (Issue #1944, diagnostic-traces 1/n under #1943)."
  documentation: "src/auto_coder/execution_trace.py"
  behavior:
    - "`TraceCollector` (`get_trace_collector()`) is a process-local singleton distinct from the existing category/message `TraceLogger`; every `StructuredEvent` (schema version 1) carries repository, item type/number, process-run id, execution id, execution-start sequence, its own event sequence, origin, stage id, display label, `EventKind` (execution-started, stage-started, stage-result, execution-finished), timestamp, and an optional explicit `Outcome` plus a deep-copied facts dict -- a missing outcome stays `None`/unknown, never a manufactured success."
    - "`start_execution(repository, item_type, item_number, origin, ...)` always mints a fresh opaque execution id and returns an `ExecutionHandle` context manager; two evaluations of the same item with identical attempt/head/timestamp get distinct execution ids and are ordered only by their atomically-allocated publication sequence."
    - "Scope propagation is explicit: `current_scope()`/`bind_scope()` (and the `run_with_scope` helper) carry an `ExecutionScope` across asyncio tasks and into worker threads, since `contextvars` already isolates concurrent tasks/threads from each other but does not auto-propagate into new threads. A late event explicitly re-scoped to an earlier execution keeps that execution's identity and original start sequence rather than being attributed to whichever evaluation started most recently."
    - "`ExecutionHandle.__exit__` always emits exactly one `execution-finished` event (unless `finish()` already did) and restores the enclosing scope even after an exception or `asyncio.CancelledError`, deriving the outcome from an explicit `set_outcome()` call, else `FAILED`/`CANCELLED`/`UNKNOWN` as appropriate; `Outcome` also distinguishes completed, accepted-handoff, deferred, skipped, blocked, and superseded so a bare completion event never by itself asserts an Issue is implemented or a PR is published/merged/cleaned up."
    - "Both the event buffer and the companion per-execution metadata map are bounded (`max_events`/`max_executions`); eviction increments `events_dropped`/`executions_dropped` and `get_snapshot()` reports `events_truncated`/`execution_metadata_truncated` rather than presenting a falsely-complete history. A fresh `TraceCollector` instance (new process run id) starts with empty history and never resurrects a prior run's executions."
    - "`get_snapshot()` returns an immutable `TraceSnapshot` whose events and facts are deep-copied on the way out (and were already deep-copied on the way in), so mutating a returned event's facts, or a facts dict passed in earlier, never alters retained evidence."
    - "Previously unseen stage identifiers, labels, and fact keys pass through unchanged (no dashboard-side registration needed). `record_legacy_or_raw()` ingests externally-shaped records (e.g. old Queue/Worker-style entries): records missing execution identity are marked `legacy=True`, and records with a missing/mismatched `schema_version` are marked `supported=False` -- neither is silently promoted into a valid, successful execution event. The existing category-based `TraceLogger` is untouched and remains fully usable during this staged migration."
    - "Recording, scope management, retention, and snapshot reads never authorize work or change business return values/exceptions: `_publish()` catches and loguru-logs any internal recorder failure (e.g. a broken sink) and continues without raising, so a traced operation's result and exception behavior are identical whether the recorder is healthy or failing."
    - "Out of scope here: instrumenting production Issue/PR routes, wiring this into the dashboard UI, persisting/replaying traces, or reconciling durable provider/PR state -- this stage owns only the shared event model and collection boundary."
